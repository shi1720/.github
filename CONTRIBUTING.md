# Contributing

Start with the repository README and its documented checks. Some repositories are complete applications; others are historical prototypes, integrations or evaluation fixtures. Match changes to that stated scope.

## Propose a useful change

For a bug, include the expected result, the observed result and the smallest reproducible example. Use synthetic data. Never include access tokens, service-account keys, student information or private customer material.

For a feature, describe who needs it, what they cannot do today and how success could be checked. Discuss a major architectural change before investing in its implementation.

## Prepare a pull request

1. Make one coherent change on a branch.
2. Add or adjust a regression test when behavior changes. For documentation-only edits, verify the commands and links you touch.
3. Run the repository's documented checks and explain any that need external services or credentials.
4. Describe the problem, resulting behavior and validation in the pull request. Include screenshots for interface changes.

AI-assisted contributions are welcome. The author remains responsible for understanding the change, reviewing the diff and validating the result. Do not claim a test ran when it did not.

Preserve existing attribution and licensing. A public repository without a license is not automatically licensed for reuse.
